# Stage 5 methodology

All examples bundled here are **SYNTHETIC DEMONSTRATIONS**, not actual crises or evidence of a reliable model. Stage 5 numerical functions have no CLI, filesystem or database dependencies. Snapshot adapters validate the exact six captured input files using unchanged Stage 1 rules before any analysis. Invalid or incomplete datasets block every calculation, even if the requested window would avoid the defect. Valid suspicious observations remain unchanged. No repair, correction approval, download or database write occurs in these commands.

## Rolling one-day historical VaR

Simple instrument returns are adjusted-close ratios minus one. Portfolio daily returns use the existing fixed long-only weights, rebalanced daily. Each return is dated by its ending price session. For forecast date t and lookback L, training contains exactly the preceding L returns, ending at the prior calendar session. The forecast does not contain the return at t. Training boundaries in exports are return dates, not the preceding anchor price date.

Loss = negative simple portfolio return. VaR is the existing empirical inverse CDF: sort L losses and select rank ceil(L × confidence), counting ranks from one. Negative VaR remains negative. An exception occurs only when realized loss is **strictly greater** than VaR; equal values are not exceptions. No epsilon is applied to this comparison. All losses/VaR are decimal returns: 0.01 means 1%. Lookbacks are positive integers, at least max(100, ceil(5/(1-confidence))), using the existing roundoff treatment at integer sample boundaries. Thus 95% requires 100 and 99% requires 500 returns. At least one additional return is needed for evaluation. Confidence is strictly between zero and one. Run separate commands for multiple confidence/lookback combinations; no forecast is silently omitted or partially filled.

For N forecasts and X exceptions, rate = X/N and expected count = N(1-confidence). Kupiec tests the null exception probability p=1-confidence against fitted q=X/N. LR = 2[log L(q) − log L(p)]. Log likelihood is X log(p)+(N−X) log(1−p). Implementation uses log1p and defines zero-count log terms as zero; q=0 or 1 has fitted log likelihood zero. A tiny negative LR from roundoff is clipped to zero. The reported asymptotic chi-square(1) survival probability is erfc(sqrt(LR/2)); no SciPy dependency. No binary reliability verdict is produced.

One evaluation is computationally allowed, but a small sample or a small expected exception count makes asymptotic inference weak. Discrete empirical VaR and ties also affect observed coverage. Overlapping training windows, clustered losses and regime changes challenge test assumptions. Kupiec measures unconditional coverage, not independence, loss severity or forecast accuracy. A high p-value is failure to reject one null, **not proof of model reliability**. The five-observation training-tail requirement does not ensure an adequate evaluation sample.

## Hypothetical shock scenarios

Schema: exactly name (nonempty string), instrument_shocks (mapping), sector_shocks (mapping). Keys must identify registered instruments/sectors. CLI rejects duplicate JSON keys. Values are finite numeric decimal simple returns, excluding booleans, at least −1. There is no upper cap on gains, but nonfinite arithmetic is rejected. No volatility, factor, additive multi-period, cash, FX, leverage or price-level shock syntax is supported.

Every registered instrument, including zero-weight instruments, needs explicit coverage by an instrument shock or its sector shock. Zero shocks must be stated explicitly. An instrument shock **overrides** its sector shock; they are never added. The effective source and overridden sector shock appear in instrument exports. All shocks are simultaneous, applied once to the starting portfolio valuation. Instrument contribution = weight × shock; sector contribution sums its instruments; portfolio return sums all contributions. Each contribution and total is shown as decimal return, percentage (100 × decimal), and base-currency amount (valuation × decimal). Positive means gain and negative means loss. Instrument shock is distinct from its weighted portfolio contribution.

No transaction costs, taxes, liquidity constraints, FX conversions or changing weights are simulated. Existing validation requires a common base currency. A scenario is hypothetical even when inputs are imported historical data.

## Observed-window replay

Both endpoints must be exact validated calendar price dates with start < end. The starting price is the anchor; the first realized return ends on the next session and the last ends on the selected end date. All observations across the full captured dataset, including every window session, must pass existing validation. No forward fill, skipped observations or synthetic repair is allowed.

Use today's supplied portfolio weights as a hypothetical daily-rebalanced strategy, not historic holdings. Starting wealth is 1 and terminal wealth is product(1 + daily portfolio return). Starting currency valuation is portfolio.valuation. Instrument P&L contribution is sum over days of starting-day wealth × instrument weight × daily instrument return, relative to initial valuation. Sector contributions sum those instrument contributions; they reconcile with compounded total return within floating-point roundoff. These are allocations of daily-rebalanced P&L, not standalone buy-and-hold instrument cumulative returns. Daily CSV includes ending wealth and day's base-currency P&L.

Synthetic provenance always produces a synthetic label; a synthetic window is never an actual historical crisis. Acquired timestamps do not reconstruct the complete historical information set. This replay is neither reconstruction of actual historic holdings nor a VaR forecast.

## Reproducibility and exports

Old risk calculations, engine version 0.2.0, saved report meanings, schema/migrations and comparison compatibility remain unchanged. Stage 5 adds analysis_version 0.5.0 and distinct kinds; it does not insert these analyses into the existing risk-report tables or loosen the existing comparison adapter. Its JSON includes the complete configuration/scenario definition, portfolio, provenance, exact input/file hashes and both versions. capture.json embeds the original six byte strings using the existing canonical snapshot format, allowing analysis after source removal. No originals are overwritten.

content_hash is SHA-256 of risklens-canonical-json-v1 serialization of the complete analysis envelope excluding content_hash: sorted keys, compact UTF-8 JSON, no NaN or Infinity, Python float representation, no trailing newline. report.json is pretty-printed for review, so its byte hash is not content_hash. Raw-byte integrity does not prove data accuracy; numerical agreement does not prove raw-byte identity. Equivalent recalculations may be compared using existing rtol=atol=1e-12 conventions, but Stage 5 does not claim verified persisted replay or extend the approved correction-impact workflow.

CSV is accompanied by metadata.json (configuration and scenario definitions) and report.json. forecasts.csv records forecast/training dates, VaR, realized loss and boolean exception; instrument/sector CSVs contain contributions; summary.csv contains portfolio amounts or coverage counts and Kupiec values. CSV exports carry input hash, mode and version fields on detailed rows. All commands refuse any existing output directory. Captures can be large because they deliberately retain raw inputs.
